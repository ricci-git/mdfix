# Оцінка готовності та пропозиції щодо розвитку `mdfix`

**Дата оцінки:** 2026-10-07  
**Версія в CLI:** 0.8.3  
**Гілка:** `master`

## Короткий висновок

`mdfix` має корисну основу для майбутнього Markdown-аналізатора: сканер файлів, блоковий парсер, моделі AST та окремі компоненти для розбору inline-елементів. Наявні тести охоплюють базову поведінку цих компонентів, а CLI запускається.

**Оцінка готовності до заявленої мети — ранній прототип, не MVP для користувачів.** На цей момент програма сканує Markdown-файли та розбирає частину синтаксису, але ще не повідомляє про помилки, не має системи правил/діагностик і не виправляє документи. Парсер inline-синтаксису не підключений до основного парсингу абзаців. Форматувальник таблиць існує як окрема, незакомічена реалізація без інтеграції у CLI.

Рекомендований наступний крок — визначити обмежений MVP: перелік підтримуваних конструкцій Markdown, категорії помилок, формат діагностики та політику безпечного виправлення. Після цього варто завершити наскрізний цикл **розбір → діагностика → попередній перегляд виправлень → застосування**.

## Що вже є

- CLI-команди `mdfix scan` та `mdfix version`.
- Рекурсивний пошук файлів `.md` з виключенням `.git`, `.venv` та `node_modules`.
- Базовий блоковий парсер для заголовків, абзаців, списків, цитат, fenced code blocks, горизонтальних ліній і таблиць.
- Моделі блокових елементів та inline AST.
- Inline tokenizer/parser для частини синтаксису: текст, `**strong**`, `*emphasis*`, inline code та прості посилання, включно з окремими вкладеними випадками.
- Окремий форматувальник таблиць у `mdfix/table_formatter.py`; тести для простих таблиць, вирівнювання ширини колонок, порожніх/відсутніх і зайвих клітинок.
- У наборі є близько 130 функцій-тестів за статичним підрахунком `def test_` у `tests/`. Це не підтверджує їх успішне виконання в цьому середовищі.

## Основні прогалини та ризики

### 1. Відсутній цикл перевірки й виправлення

CLI показує знайдені файли, але не аналізує помилки й не має команди виправлення. Немає моделі результату перевірки, де можна було б представити правило, повідомлення, рівень серйозності, позицію в документі та можливу зміну.

**Наслідок:** користувач поки не може використати програму для заявленої мети — знайти й виправити помилки Markdown.

### 2. Inline AST не є частиною основного результату парсингу

`Paragraph` має поле `inline`, однак `parse_elements()` створює абзаци лише з `text`; поле inline-вузлів лишається `None`. Inline-парсер викликається окремо й не з’єднаний із результатом `parse_markdown()`.

**Наслідок:** аналіз і форматування inline-вмісту не можна надійно виконувати наскрізно на звичайному документі.

### 3. Обмежене покриття Markdown

Поточні компоненти реалізують власну спрощену підмножину синтаксису. Зокрема, парсер таблиць розділяє рядки за символом `|`, а inline-парсер шукає прості маркери та межі посилань без повної обробки екранування й усіх варіантів синтаксису. Обробка вкладених і неоднозначних конструкцій має бути визначена й перевірена явно.

**Наслідок:** на реальних документах можливі хибні діагностики, втрата структури або небажані зміни, якщо виправлення застосовувати без суворих гарантій.

### 4. Форматувальник таблиць не інтегрований і ще не є частиною репозиторію

`mdfix/table_formatter.py` та `tests/test_table_formatter.py` позначені Git як незакомічені нові файли. Функцію `format_table()` можна викликати напряму, але її не викликає CLI або загальний форматувальник документів. Вона також не зберігає вихідний вигляд таблиці: наприклад, інформація про вирівнювання з розділювачів колонок не представлена у моделі `Table`; клітинки, що містять `|`, потребують окремої обробки.

### 5. Версії й документація суперечать коду

- `mdfix/version.py` визначає `0.8.3`, і команда CLI показує `mdfix 0.8.3`.
- `pyproject.toml` задає версію пакета `0.1.0`. Отже, метадані зібраного пакета можуть не відповідати версії CLI.
- README вказує версію `0.7.0` і `45 tests passed`, а roadmap досі позначає форматування таблиць та повний inline-парсер як заплановані.
- `docs/PROJECT_STATE.md` описує робочу копію як чисту, тоді як на момент оцінки Git показував два незакомічені файли.
- `docs/INLINE_AST_DESIGN.md` називає Inline Parser майбутнім компонентом, хоча окрема реалізація вже є.

**Наслідок:** користувачі й розробники не мають одного достовірного джерела стану проєкту.

### 6. Пошук файлів включає деякі службові каталоги

Під час перевірки `mdfix scan .` команда включила `.pytest_cache/README.md`. Цей каталог відсутній у `DEFAULT_EXCLUDES`.

**Наслідок:** сканування кореня репозиторію може захоплювати документацію кешів та інші нецільові Markdown-файли.

### 7. Перевірку тестів не вдалося завершити в поточному середовищі

У вибраному `.venv` немає модуля `pytest`: команда `/home/ricci/mdfix/.venv/bin/python -m pytest -q` завершилася помилкою імпорту. Тому успішність набору тестів не підтверджена цією оцінкою. У `pyproject.toml` визначені runtime-залежності, але не описані залежності для розробки/тестування.

## Рекомендований план робіт

### Етап 1 — Зафіксувати MVP та інтерфейс перевірки

1. Визначити підтримувану підмножину Markdown і бажану сумісність (наприклад, конкретні конструкції CommonMark/GFM).
2. Узгодити початковий каталог правил: назва/ідентифікатор, опис, рівень серйозності, умови спрацювання та доступність автоматичного виправлення.
3. Визначити стабільну модель діагностики: шлях, рядок/колонка або діапазон, код правила, повідомлення й запропоноване виправлення.
4. Розділити режими «лише перевірити», «показати diff» та «застосувати виправлення». До появи перевіреного diff не змінювати файли за замовчуванням.
5. Узгодити поведінку CLI для ненульового результату перевірки, помилок читання/запису й передавання шляхів.

**Критерій завершення:** описаний MVP із прикладами вхідного Markdown, очікуваних діагностик і очікуваних виправлень.

### Етап 2 — Довести парсинг до наскрізного використання

1. Під’єднати inline parsing до абзаців та інших текстових блоків, де це передбачено специфікацією MVP.
2. Формалізувати розбір таблиць: escaped pipes, необов’язкові крайні `|`, відсутні/зайві клітинки та маркери вирівнювання.
3. Визначити поведінку для некоректного або непідтримуваного Markdown: зберегти як текст, видати діагностику або відмовитися від автоматичної зміни — без мовчазної втрати вмісту.
4. Перевіряти збереження вихідного тексту для конструкцій, які не виправляються.

**Критерій завершення:** інтеграційні тести показують, що реальний документ проходить через `parse_markdown()` і повертає очікувану структуру inline та блочних вузлів.

### Етап 3 — Безпечні виправлення і форматування таблиць

1. Додати renderer/serializer для моделей документа або застосовувати локальні текстові зміни з відомими діапазонами джерела.
2. Інтегрувати `format_table()` лише після того, як модель може відобразити потрібні властивості таблиці й визначено політику щодо вмісту клітинок.
3. Вимагати точного diff до запису, збереження newline/encoding та ідемпотентності форматування.
4. Для файлів із невпевнено розібраними областями відключати автоматичну зміну цих областей і повідомляти про причину.

**Критерій завершення:** форматування не змінює семантику підтримуваних таблиць, повторний запуск не створює нового diff, а проблемні випадки мають явну поведінку.

### Етап 4 — Тести, інструменти та релізна готовність

1. Описати pytest та Ruff у dev/test dependency group або іншому документованому механізмі встановлення розробницького середовища.
2. Додати інтеграційні тести CLI для діагностик, diff, коду завершення й застосування виправлень.
3. Додати регресійні приклади з реальних Markdown-документів; окремо перевіряти невідомі синтаксичні випадки, Unicode, escaped delimiters і таблиці.
4. За можливості додати property-based тести для збереження вмісту та ідемпотентності.
5. Встановити єдине джерело версії та синхронізувати `pyproject.toml`, `mdfix/version.py`, README і стан проєкту.
6. Оновити README та архітектурну документацію після погодження обсягу MVP; видаляти або уточнювати застарілі обіцянки.
7. Переглянути список виключень сканера, щоб він охоплював потрібні каталоги кешів/збірок без надмірного виключення користувацьких файлів.

**Критерій завершення:** чисте встановлення dev-залежностей, повний успішний тестовий запуск, Ruff без помилок, узгоджена версія в CLI та метаданих пакета.

## Пропонований порядок пріоритетів

| Пріоритет | Робота | Чому зараз |
|---|---|---|
| P0 | Узгодити обсяг MVP та модель діагностик/виправлень | Без контракту неможливо перевірити, що саме вважається завершеним продуктом |
| P1 | Інтегрувати inline AST, визначити підтримуваний діалект і підсилити парсинг таблиць | Це основа для надійного виявлення помилок без спотворення документа |
| P1 | Додати аналіз, попередній перегляд diff і контрольоване застосування | Це перетворює парсер на інструмент, корисний користувачеві |
| P1 | Виправити джерело версії та актуалізувати документацію | Інакше встановлена версія й обіцянки в документації можуть вводити в оману |
| P2 | Інтегрувати та завершити formatter таблиць | Функція вже почата, але ще не доступна наскрізно й потребує тестів крайових випадків |
| P2 | Розширити виключення сканера й CLI-тести | Покращує поведінку у звичайних репозиторіях і захищає UX від регресій |
